## 1. Screens & states

The module renders three things itself (language dialog, toast text, alias avatar element) and globally re-skins every other screen (dark palette, Chinese text). Entry points for its two user-facing actions live in Settings and in the Chat "+" menu.

Modal confirmation dialog (added 7/2026 after user feedback: "must have a Confirm button, don't switch on tap").

- **Entered from**: Settings › Preferences › "Language" row (`onclick="openLangDialog()"`, index.html line 1577) and the Chat-view "+" popover item `translate` / "Language" (match.js `toggleChatPlusMenu`, line 154; the popover closes first, then runs).

### 1.4 Chinese mode (global text rewrite)

No screen of its own. When `cl_lang === 'zh'` at boot: (1) `translateTree(document.body)` walks every text node and every `input/textarea[placeholder]`, (2) a `MutationObserver` (`childList + subtree` on `document.body`) translates every node added afterwards. Rules in §5. `<html lang="en">` is static and **never changes** — do not use it as a language signal (CLAUDE.md 8/13 lesson).

Validation / disabled states: none. Race guards: none needed — the dialog is single-instance per open (multiple opens would stack, but every entry point is a tap on a row that is only reachable when no dialog is up). The observer is never disconnected.

Reload consequences the iOS port must reproduce semantically: after a language change the H5 app cold-boots — any in-progress state (drafts, scroll positions, open overlays, SSE connection, timers) is lost; the token in `localStorage.cl_token` survives so the user stays logged in. On iOS, switching the locale should instead re-render in place, but the *policy* to note is that H5 never keeps unsaved state across a language switch, so nothing depends on that.

## 3. API calls

**None.** The module performs no fetch/XHR/SSE. Specifically:

- Language and theme are **device-local preferences** (never sent to `/settings`, never read from the server). The backend `User.settings` JSON has no language key; the account-level toggles on the Settings page (`pushEnabled`, privacy flags) are a different mechanism (settings.js).
- Server-provided text that is localised client-side using `getLang()` (owned by other modules but relies on this one): notification titles/bodies (notifications.js `localizeNotif`, 16 titles + 7 static bodies + 10 regex bodies), questionnaire `title`/`titleEn` and option `label`/`labelEn`, and the anonymous `aliasSeed` (backend never sends a display name for anonymous authors — see §7).
- After `reload()`, the normal boot sequence issues its own calls (core/auth maps: `checkUserState`, `/auth/me`, SSE start…). Nothing i18n-specific is requested.

## 5. i18n mechanics and the complete string tables

### 5.1 Model

- The DOM's source of truth is **always English** (index.html markup and every JS template literal are written in English). Chinese is produced by an in-place rewrite of text nodes. There is no reverse mapping, which is why switching to English requires a reload.
- Lookup is **exact whole-text match on the trimmed text node**: `trimmed = nodeValue.trim(); if (ZH[trimmed]) nodeValue = nodeValue.replace(trimmed, ZH[trimmed])` — leading/trailing whitespace is preserved, substrings are never translated, and a text node whose content is `"3 cells"` will not match the key `cells`. Anything composed with dynamic values must therefore be localised in JS with a `getLang() === 'zh' ? zh : en` ternary and (usually) marked `data-no-i18n` so the observer leaves the already-localised result alone.
- Only **text nodes** and the **`placeholder` attribute** of `input`/`textarea` are translated. `title`, `aria-label`, `alt`, `value`, `<option>` labels set via `textContent` (those are text nodes → translated), CSS `content`, and `<title>` are not (placeholders use the separate `ZH_PLACEHOLDER` table).
- `metaLabel(v)`: `if (!v) return v; if (getLang() !== 'zh') return v; return META_ZH[v] || ZH[v] || v;` — display-only translation for profile metadata values (school/city/major/nationality/grade). The stored/PUT value is always the English canonical string. Note the fallback into the global `ZH` dictionary: values like `Undergraduate`, `Master`, `PhD`, `Other`, `Male`, `Female`, `Nationality` resolve through `ZH`. `META_ZH` and `ZH` share **no** keys (verified).
- The observer never runs in English mode (`startI18n` returns early), so English mode has zero translation overhead and zero risk of mistranslating user content.

### 5.2 Observer and `data-no-i18n` rules

`startI18n()` (runs at import, or on `DOMContentLoaded` if the document is still loading):

1. `if (getLang() !== 'zh') return;`
2. `translateTree(document.body)`:
   - if the root element itself has `data-no-i18n` → return without walking.
   - `TreeWalker(SHOW_TEXT)` with `acceptNode` = `isInNoI18n(node) ? FILTER_REJECT : FILTER_ACCEPT`; collect all nodes first, then `translateTextNode` each (avoids mutating while walking); then `translatePlaceholders(root)`.
   - whole thing in try/catch (silently ignores odd roots).
3. `new MutationObserver(muts → for each addedNode: text node → translateTextNode; element → translateTree(node))` observing `document.body` with `{childList: true, subtree: true}`.

`isInNoI18n(node)`: starting at the node (or its parent for text nodes) walk up `parentElement` until an element with attribute `data-no-i18n` is found → true. Cost O(depth) per text node.

What **is** observed and translated: any `innerHTML =` / `appendChild` / `textContent =` on an element (setting `textContent` replaces the child text node, i.e. a `childList` mutation whose added node is the new text node → translated). What is **not**: `node.nodeValue = …` on an existing text node (`characterData`), attribute changes (so a placeholder set later via `el.placeholder = 'Search posts'` stays English unless the module calls `window.translatePlaceholders(el)` — which **currently has zero external callers**; chat.js sets its placeholder with a zh ternary instead).

`data-no-i18n` contract (comment in source): user-generated content — chat bubbles, nicknames, notes, post titles/bodies, comment text, profile bio, school badges after `metaLabel`, notification titles/bodies after `localizeNotif`, timestamps, counters — may coincidentally equal a UI key (e.g. a post titled "Today" or a nickname "Chat"), so every element rendering user content is marked and its entire subtree is skipped. Usage counts today: square.js 29, match.js 18, profile.js 16, index.html 11 (brand `UNIMATCHA`, `BETA`, version line `Unimatcha v2.4.0`, `#filter-sheet-title`, `#pd-header-author`, `#chat-partner-name`, `#chat-partner-location`, `#edit-age-hint`, `#settings-email`), chat.js 10, notifications.js 7, i18n.js 7, questionnaire.js 2, auth.js 1. The inverse trap (CLAUDE.md 8/14): marking a whole `<p>` `data-no-i18n` also blocks the UI label inside it — keep the mark on the user-content span only and leave UI labels outside.

A second reason some strings bypass the dictionary: very short generic words were removed from `ZH` in 7/2026 (`Title`, `Note`, `Date`, `YOU`) and `Edit` was deliberately kept out (8/13 lesson: too short, would translate user content) — `#filter-sheet-title` is set by `openFilterSheet` per language with `data-no-i18n`. Note that `Today`, `All`, `Both`, `Add`, `Send`, `Chat`, `Free`, `Male`, `Female`, `Other`, `Match`, `Bio`, `City`, `Major` **are** in the dictionary now, so any user content rendered *without* `data-no-i18n` that exactly equals one of these would flip to Chinese.

Algorithm (must be bit-identical on iOS so an anonymous author looks the same on web and app):

```
n   = ToUint32(Number(seed))          // JS `Number(seed) >>> 0`; seed arrives as number or numeric string
adj = n % 16
ani = (n >>> 8) % 16                  // animal index
emo = (n >>> 8) % 16                  // same index as animal → emoji always matches the animal
bg  = (n >>> 16) % 16
name = zh ? ADJ_ZH[adj] + ANI_ZH[ani] : ADJ_EN[adj] + " " + ANI_EN[ani]   // no space in zh
```
Examples from production logs: `Cozy Heron` ↔ `暖心的白鹭`, `Quiet Quokka` ↔ `安静的小袋鼠`, `Noble Hare`, `Cozy Marten`. Same seed → same animal, same emoji, same background in both languages. `seed` is an opaque per-post HMAC output from the backend (`aliasSeed`), so the same person has different aliases on different posts by design (8/19 privacy fix) — never try to correlate. Fallback when `aliasSeed` is null: square.js shows `p.anonymousAuthor?.nickname || 'Anonymous'`.

## 7. Gotchas for the iOS implementer

1. **Language is device-scoped, default English, not synced to the account.** Store in `UserDefaults`; do not clear on logout; do not send to the backend. Same for dark mode (H5 has no "follow system" option — only explicit light/dark, default light).
2. **The dictionary is keyed by English source text and matched whole-string.** Ship the tables above as `en`→`zh` pairs; every composed string (counts, names, dates) needs a separate localised template — H5 does this with `zh ?` ternaries listed in §5.9, and each of those ternaries is the spec for that string.
3. **Never translate user content.** The `data-no-i18n` rule is the H5 embodiment of: nicknames, notes, chat text, post titles/bodies, comments, bios, interest chips, school names *after* `metaLabel`, and notification bodies must be rendered verbatim. On iOS this is automatic (no DOM rewrite) but the *inverse* trap exists: do not run backend strings through `NSLocalizedString`-style lookup by value.
4. **Metadata values are English canonical strings in the API.** Profile `school`/`city`/`major`/`nationality`/`grade` are stored and PUT as the English value; only the *display* is translated via `META_ZH` (+ `ZH` fallback). Dropdowns must keep the English value as the selection key and show `metaLabel(value)` as the label; a value missing from the map shows untranslated. Nationality zh labels are country names (Chinese → 中国), not demonyms.
5. **Anonymous alias must match the web bit-for-bit** (§5.6): `UInt32(truncating: seed)`, `adj = n % 16`, `animal = emoji = (n >> 8) % 16`, `bg = (n >> 16) % 16`; zh concatenates without a space. Alias/avatar are per-post (seed differs across posts for the same person); never show the real user or try to correlate. When `aliasSeed` is null fall back to `anonymousAuthor.nickname` or "Anonymous".
6. **Alias avatar sizing lesson (8/19):** emoji glyphs overflow a box of the same pixel size; H5 derives emoji font-size ≈ 0.62 × container size (16 px box → ~10 px emoji, 32 px → ~20 px). Background colours are the fixed pastel list; do not randomise per render.
7. **Short dictionary keys are a data-pollution risk** (`Today`, `All`, `Both`, `Add`, `Send`, `Chat`, `Free`, `Male`, `Female`, `Other`, `Match`, `Bio`, `City`, `Major`, `Title` as placeholder only) — the reason H5 marks user content. `Edit`, `Note`, `Date`, `YOU` were deliberately removed/kept out for this reason; the filter-sheet title "Edit"/"编辑" is set per language by `openFilterSheet`. Nine keys are duplicated in the source object literal with identical values (harmless; last wins).
8. **Placeholders are a separate table** and attribute changes are not observed; `window.translatePlaceholders` exists for that but is unused — modules localise placeholders imperatively (chat.js input, `Search posts` etc. rely on the boot pass over index.html).
9. **Toast copy for dark mode is English-only** ("Dark mode on"/"Light mode on"); iOS should localise it (H5 doesn't).
10. **`<html lang>` is always `en`; `document.documentElement.lang` is not a language signal** — a real bug was caused by checking it (`reasonLabel`, 8/13). Use `getLang()` semantics only.
11. **Language switch = full reload in H5** (state loss, SSE reconnect, splash). iOS should re-render in place, but remember there is no server-side language, so the reveal-date/countdown/weekday copy in match.js, notification localisation, questionnaire `titleEn`/`labelEn` selection and content pages must all key off the same local preference at render time.
12. **Dark palette specifics**: warm black (#121110 base, R ≥ G ≥ B), neon green/pink unchanged, black text kept on neon buttons, ivory text-cards intentionally stay light in dark mode (accent), dark text rules use `!important` (per-screen overrides must too). Legacy comments may mention #15151a — the current tokens are the warm set in §1.3.
13. **Content pages are whole-document alternates**, not sentence-level translations; keep them as two complete localised documents (`title` + sections). Both reference `contact@unimatcha.ai` (the only support address; older `support@campuslove.app` was purged 7/18).
14. **Observer cost/ordering**: translation runs synchronously on every DOM insertion in zh mode. iOS has no equivalent overhead, but note that any H5 string localised *before* insertion must be wrapped `data-no-i18n` to avoid double translation — the cross-module `zh ?` sites already do this; when porting, the presence of `data-no-i18n` on an element is a reliable signal that "this text is user content or already localised".
