# Unimatcha 运营就绪度评估

> 回答的问题是：**这套软件现在离"真正投入运营"（有真实用户、收真实钱、稳定跑下去）还差什么**。
> 编写方法：交叉核对 `BACKLOG.md`（2026-08-13 版，已偏旧）、`SCHEDULING.md`、`CLAUDE.md` 每日日志（截至 2026-09-01 最新一条）、`docs/PROJECT-CHECKLIST.md`/`FEATURES-*.md`，并对本次列出的每一项**现场核实了代码/配置**（见各条"核实方式"）。本机（新环境）没有到生产服务器的 SSH 密钥，无法直连核对生产环境当前实际配置，凡是"据日志"而非"本次核实"的条目已标注。
> 编写日期：2026-09-04。

---

## 一、结论先说

底层能力已经很扎实——匹配算法、双端后台、H5 全功能、SSE 实时、邮件验证码、迁移+备份体系、iOS 原生客户端都已完成并有真实生产验证记录。**但"能跑"和"能对外真正运营（尤其是收真实用户的钱）"之间，还有几类明确的缺口**，大致分四种性质：

1. **工程未做，且是硬阻塞**——最典型是没有接任何真实支付渠道，能量购买全程是 mock；iOS 若要上架，还缺一条 Apple 强制要求的自助注销账号路径。
2. **工程未做，但产品已经决定"可以先不做"**——比如 matching-ml 用规则版 mock 而非真实大模型上线，这是 `BACKLOG.md` P0-6 明确拍板过的可接受选项，不是遗漏。
3. **需要真人拍板或真人运营，不是代码能解决的**——学生认证审核谁来看、内容审核队列谁来处理、客服渠道是否够用、公司主体/收款资质。
4. **基础设施韧性缺口**——单机部署、无监控告警、无 CI、备份未做异地（这条是用户已经拍板"先只本地"的决策，记录为已知风险而非遗漏）。

下面按"硬阻塞 → 需要真人拍板 → 韧性缺口 → 已经拍板不做" 的顺序展开，最后给 iOS 上架单独列一节（因为最新完成、最贴近你现在的工作）。

## 二、硬阻塞：不做就无法真正对外收费运营

### 2.1 没有任何真实支付渠道 —— 这是最大的缺口

**核实方式**：`grep -rln "stripe\|alipay\|wechatpay\|paypal" apps/api apps/h5` 全仓零命中；`apps/api/src/energy/energy.service.ts` 第 285-339 行注释写明"本期 mock：仅生成订单号 + 返回 `{ mock: true }`"，`rechargeMethod: 'mock'` 直接落库。

**现状**：能量购买（应用内唯一的付费入口）从下单到"支付成功"全程是假的两步确认流程，没有对接微信支付/支付宝/Stripe 中任何一个真实收单渠道。也就是说，**现在这套系统技术上完全没有能力向任何人收一分钱**。

**要做什么**：
- 确定收款主体（个人？公司？境外主体收英镑还是境内主体收人民币，直接决定接哪家）。
- 接入对应支付网关（国内走微信支付/支付宝商户号；面向英国用户可能要 Stripe），改造 `energy.service.ts` 的 purchase/confirm 两步为真实下单+回调验签。
- 涉及发票/税务合规，这部分不是工程问题，需要你或财务顾问定。

### 2.2 ~~iOS 缺一条 Apple 强制要求的自助账号注销路径~~ 已完成（2026-09-04）

**当时的现状**：注销账号是"发邮件人工处理"，没有应用内一键自助注销，Apple 5.1.1(v) 强制要求这条，不补大概率被拒审。

**已落地**：后端 `POST /users/me/delete`（原地匿名化，非硬删——保留 Match/Message/SquarePost 等历史行，避免破坏对方的聊天记录/匹配历史；email/密码作废、Profile 全部 PII 清空、nickname 固定改为 "Deleted User"，早于隐私政策承诺的 30 天时限）+ 二次确认（重新输入当前密码，与 `changePassword` 同一套校验）+ JWT 策略同步拒绝已注销账号的旧 token（不止是堵住重新登录）。H5 与 iOS 两端设置页都加了入口（危险操作两步确认：先警示后果，再要求密码）。新迁移 `20260831120000_init` → `20260903180716_add_deleted_user_status`，纯增量（新枚举值 + 一个可空列），零破坏性。

**验证**：后端——真实 Postgres 端到端跑通（错误密码拒绝且不改动任何数据、正确密码后 status/email/密码哈希/昵称/各项 PII 全部核对、二次调用被拒绝、原邮箱无法再找到账号），`tsc --noEmit` 0 错。H5——生产构建通过，浏览器实测两步确认卡中英双语渲染正确（含动态注入文案的翻译）、密码框确认走 `type="password"` 遮罩。iOS——全树 typecheck 0 错，模拟器 Debug 与真机 SDK Release 均 `BUILD SUCCEEDED`，装机自检 20/20 通过；受限于我不代为登录真实账号，未能截图核对设置页这一具体屏幕的最终排版（逻辑与 UI 组件均复用已验证的 `changePassword` 同款模式）。

### 2.3 每周匹配的正式节奏一直没有"运营切换"

**核实方式**：`SCHEDULING.md` 第 19 行"当前现状：配置是 `0 17 * * 5`（每周五 17:00，北京时间）"；`BACKLOG.md` P0-3 从未被标记完成，多次日志（7/17、7/21 等）反复记"待办：正式公布 cron 运营切换"。本次未连接生产库复核当前是否已改。

**现状**：技术上系统本来就是"每周一轮"（cron 到点就自动算+公布），**这本身已经能运营**，缺的是仪式感——"周五开池 + 周日公布 + 开场公告"这套产品叙事从设计出来后就没有正式切换上线，一直停在默认的"周五 17:00 算完立即公布"。

**这算不算硬阻塞**：不完全算。如果你能接受"每周固定时间直接公布"这个更简单的模式，那这条其实**现在就是可运营的**，只是缺一句开场文案；如果你要"周五开始、周日公布"这种有仪式感的两段式体验，需要按 `SCHEDULING.md` 方案 A 改一次 cron 配置（纯配置，零代码）。真正的两阶段"轮次"系统（方案 B，能人工审核结果再放出）还没做，属于 P1，不阻塞上线。

## 三、需要真人拍板或真人运营，代码解决不了

| 事项 | 现状 | 缺什么 |
|---|---|---|
| 学生认证审核 | 系统已有"学生证照片 + 邮箱验证码"两段式认证流程，验证码对了也只是置成 `pending`，必须人工看照片才能置为 `verified`（`users.service.ts:415-427`，这是刻意设计的反作弊关卡） | **谁来审？** 现在没看到任何专职审核人力的安排记录，只有学生会/团队角色的后台入口 |
| 内容审核（举报队列、下架） | admin 后台功能完整（学生会审本校、团队审全量），代码侧已验证 | 同上，需要真人日常处理，不是一次性配置 |
| 客服渠道 | 目前只有 `contact@unimatcha.ai` 一个邮箱（注销、举报、支持全走它） | 用户量上来后单邮箱是否够用；`BACKLOG.md` P2-9 提到"客服工单系统"是远期项，量小时邮箱够用 |
| 收款主体与合规 | 无 | 见上面 2.1，需要你或财务/法务先确定主体 |
| 隐私政策/用户协议的法律有效性 | 文案是本项目历次会话写的中英双语条款（内容合理、覆盖了数据保留/申诉等），但**没有律师审阅过的记录** | 如果要严肃对外运营（尤其面向英国大学生，UK GDPR 管辖），建议至少找律师过一遍——匹配偏好本质上会推断性取向这类"特殊类别数据"，欧盟/英国 GDPR 对这类数据有更高要求 |

## 四、基础设施韧性缺口

**核实方式**：全仓搜索 `.github/workflows` 目录不存在（无 CI）；`CLAUDE.md` 8/31 日志明确记录"用户决策：异地暂不配、先只本地"（备份体系已做，异地是用户自己拍板延后，不是遗漏）；7/17、8/31 日志各记录过一次真实 DNS/DNSSEC 事故导致全站不可访问。

| 项 | 现状 | 风险 |
|---|---|---|
| 全仓无 CI | 确认无 `.github/workflows`，所有验证靠人工跑 tsc/jest/build | 改动全靠自觉跑测试，没有 PR 级别的自动化门禁，规模变大后容易漏测 |
| 单机部署 | 一台 DigitalOcean droplet（伦敦，2vCPU/4GB）扛全部服务，无高可用 | 机器故障=全站下线；`BACKLOG.md` P2-8 有拆分方案，但要到 DAU 上千或 CPU 持续 70%+ 才需要 |
| 备份只本地 | 每日自动备份+已做恢复演练验证，但**未配异地**（用户已拍板的决策） | 如果整机丢失（非误删而是机器本身出问题），本地备份也一起没了；风险已知，是否要补异地由你定 |
| 无监控告警 | 全仓未见 Sentry/UptimeRobot 之类的错误追踪或可用性监控 | DNS 那两次事故都是用户自己发现"打不开"才排查的，没有自动告警提前发现 |
| 域名/DNS 历史脆弱 | 已发生两次全站级 DNS 事故（NS 被劫到 Spaceship 停放服务器、DNSSEC 残留），`CLAUDE.md` 已记录教训但没有自动化监控防第三次 | 建议至少加一个免费的 uptime 监控（如 UptimeRobot）盯官网/API 可达性，出问题第一时间知道 |

## 五、iOS 端专项上架清单

这块是最新完成的部分，单独列一节。**代码/编译/模拟器层面已经验证过**（全树 typecheck 0 错、模拟器 Debug 构建成功、真机 SDK Release 构建成功、20 项自检套件全过），但"能编译"和"能上 App Store"之间还有一段纯运营/账号层面的工作：

- [ ] **自助注销账号**——见上文 2.2，这是唯一会导致审核直接被拒的技术缺口。
- [ ] **加入 Apple Developer Program**（$99/年）——目前 `project.yml` 里 `DEVELOPMENT_TEAM` 是空的，没有这个就无法签名、无法上传 App Store Connect，连 Apple Wallet 门票（`BACKLOG.md` P1-8）也一并卡在这里。
- [ ] **真机验证**——目前只在模拟器上跑过，从未装到真实 iPhone 上测试过（相机/相册权限弹窗、真实网络环境下的表现、性能）。
- [ ] **App Store Connect 素材**——各机型截图、App 预览（可选）、隐私"营养标签"问卷（要如实申报收集了哪些数据类别，例如位置校区、聊天记录、照片）。
- [ ] **TestFlight 内测一轮**——建议先内测再直接提审，能提前挡掉真机才会暴露的问题。
- [ ] **深链接**——如果以后 H5/邮件里想跳转到 App 内具体页面，Universal Links 还没配置，属于锦上添花不是阻塞项。

**已经不是问题的部分**（避免重复检查）：App 图标已经是正式设计稿（不是占位图，268KB 的 1024×1024 真实素材），Info.plist 权限说明文案齐全，ATS 配置正确区分了 Debug/Release。

## 六、已经拍板"暂不做"，不算缺口

这几项容易被误当成"还没做完"，实际上是产品已经明确决定延后的，列出来是为了不重复纠结：

- **matching-ml 接真实大模型**——现在 `LLM_BACKEND=mock`（规则版），`matching-ml/README.md` 里写得很清楚这是刻意的冷启动策略，输出 JSON schema 和真模型完全一致，以后切一个环境变量就能换，代码不用动。`BACKLOG.md` P0-6 已经拍板"规则版可以直接上线"。
- **Apple Wallet 电子门票**——前端逻辑已就绪，唯一卡点是需要 Apple Developer Program 证书，会随 iOS 上架流程一起解决（见五）。
- **原生 Android**——从未规划过，移动端策略是 H5 兜底 + iOS 原生，如果要覆盖 Android 用户是一次新的立项决策。
- **应用内换肤系统**——上次你问起时我给过建议：不做全套换肤，理由和轻量替代方案见对话记录，这里不重复。
- **真实推送通知（APNs/Web Push）**——H5 和 iOS 现在都只有应用内提示（SSE 实时 + 轮询兜底），没有锁屏/系统级推送，`BACKLOG.md` P2-6 列为远期项。
